# ADR-001：平台定位——雲端版為主力；編輯平台不拆分

- 狀態：已採納（2026-07-07）
- 事實依據：docs/ARCHITECTURE.md（先讀它再讀本檔）
- 標註慣例：【事實】= 已查證或官方規格；【建議】= 本 ADR 的判斷，可被推翻，推翻時在此檔補記

## 背景

專案接下來要做：動畫編輯、spritecook 素材匯入、AI 生成、角色市集。
需要先回答兩個問題：(1) 現有 Firebase 雲端架構撐不撐得起這些擴充？瓶頸在哪？
(2) 指令／動畫編輯器要不要拆成獨立子專案？

## 決策 1：確認 Firebase 雲端版為主力，桌面版維持維護模式

【建議，理由如下】
- 雲端版的部署模型（fork → secrets → CI → 使用者自己的 Firebase）已經跑通，
  使用者端零安裝，這是對 streamer 最低的門檻。
- 桌面版價值在「本機能力」（視窗偵測、免雲端、SOOP 社群模式），屬利基需求。
- 共用核心（character.js / chatProcessor.js / panel.html）讓桌面版維護成本趨近於
  「跟著共用檔自動獲得改進」，不需要主動投資。
- **執行含義**：新功能一律「雲端優先」設計；桌面版只要求「不壞」（測試綠、面板能開），
  不要求功能對等。桌面版獨有功能除非有明確需求，不再擴充。

## 決策 2：承載力評估——現有架構撐得起，前提是守住三條紅線

### Spark 免費方案限制（【事實】來源標註）

| 限制 | 數字 | 來源與查證狀態 |
|---|---|---|
| RTDB 同時連線 | 100 | 使用者提供＋模型知識（截至 2026-01）。上線市集前請至 firebase.google.com/pricing 複核 |
| RTDB 儲存 | 1 GB | 同上 |
| RTDB 下載 | 10 GB／月 | 模型知識（截至 2026-01），未線上查證 |
| Hosting 儲存 | 10 GB | 同上 |
| Hosting 流量 | 約 360 MB／天 | 同上 |
| Cloud Functions | Spark 不可部署（需 Blaze） | 模型知識（截至 2026-01），未線上查證 |
| Cloud Storage | 新專案免費層已收緊，可能需 Blaze | 模型知識（2024-10 政策變動），**設計上直接不依賴 Storage** |

### 為什麼撐得起：quota 是「每使用者一份」

架構的根本特性：**沒有中央伺服器**。每個 streamer 是自己 Firebase 專案的唯一租戶：
- 同時連線：overlay 1 條 + panel 開著 1 條 ≈ 2–5 條，離 100 很遠。
- RTDB 儲存：現行 config 只有幾十 KB。就算未來每個角色包以 base64 存 RTDB（約 1–2 MB/包），
  裝 50 個包也才 ~100 MB。
- Hosting 流量：內建素材 ~3.5 MB，只有 streamer 自己的 OBS 和 panel 會載入
  （觀眾看的是 OBS 合成後的影像，不會碰這個網站）。全站 no-cache，每次開 OBS 重載一次，
  一天開 10 次也才 35 MB，離 360 MB/天很遠。
- 結論【建議】：**編輯器、角色包、AI 生成（使用者自帶 API key）全部可以在 Spark 內完成，
  不需要升級 Blaze**。需要中央基礎設施的只有「市集」，而市集另有不花錢的解法
  （GitHub 當註冊中心，見 ADR 與 docs/designs/marketplace.md）。

### 三條紅線（新功能設計時的判準，違反任一條就要重新設計）

1. **大資料不進 `/config`**。overlay 對 `/config` 是整節點訂閱，任何欄位變更都整包重推。
   角色包 base64 素材必須放獨立頂層節點（如 `/packs`，一次性讀取），並同步改 database.rules.json。
2. **不引入中央伺服器、不依賴 Cloud Functions / Cloud Storage**。任何「所有使用者共用一個後端」
   的設計都會把 quota 從「每人一份」變成「大家搶一份」，並強迫維護者付費。
3. **不破壞 fork 升級路徑**。使用者更新 = GitHub「Sync fork」→ CI 自動重部署。
   所以 RTDB 既有資料必須永遠能被新版程式讀懂（格式只加不改；讀取端做預設值容錯），
   絕不能要求使用者「升級前先手動改資料庫」。

### 真正的瓶頸排序（不是 Firebase quota）

| # | 瓶頸 | 現況 | 對策（指向文件） |
|---|---|---|---|
| 1 | **fork 升級的資料相容**：使用者哪天 Sync fork，RTDB 裡是舊資料 | 目前靠讀取端 `?? 預設值` 硬扛，沒有版本欄位 | PLAYBOOK §格式演進：只加不改＋讀端容錯範例 |
| 2 | **YouTube quota 用罄體驗**：403 後輪詢永久停止（index.html 約 L224），使用者只看到角色不動 | 桌面版 panel 有「配額已用完」badge；**雲端版 panel 無任何提示**（web 模式不提供狀態監控，panel.html 約 L419–421）——這是缺口 | 改善屬 backlog（自動午夜重試＋雲端提示）；不阻塞新功能 |
| 3 | **自訂素材的存放與分發**：目前素材只能進 repo 由 Hosting 供檔（要 redeploy） | 缺口 | docs/specs/character-pack-format.md 決定存放策略 |
| 4 | 上手門檻（15 分鐘、6 個 secrets） | 可接受，教學已寫得很細 | 不動架構；有餘裕再做 setup 精靈 |

## 決策 3：編輯平台**不拆**獨立子專案，做在現有 panel 部署內

### 選項比較

| 選項 | 內容 | 成本 | 判定 |
|---|---|---|---|
| A. 留在現有部署（panel 加分頁或新增一頁 editor.html，同 repo 同 CI） | 編輯器直接讀寫使用者自己的 RTDB，auth 現成 | 幾乎零新 infra；panel.html 需模組化以免膨脹 | ✅ 採納 |
| B. 獨立靜態站（中央部署一份編輯器，檔案進出） | 所有使用者共用一個編輯器網站 | 新 repo＋新部署＋「把成品搬回自己 Firebase」的斷點：要嘛手動下載上傳、要嘛讓使用者貼 firebaseConfig 連到自己資料庫（易錯、教學成本高、跨版本相容矩陣） | ❌ 現階段不做 |
| C. 拆 npm workspace / monorepo 套件 | 工程潔癖 | 建置鏈複雜化，違背「純靜態、免 build」的現有簡單性 | ❌ |

【建議】採 A。關鍵理由：**這個產品的分發單位是「fork」**——使用者拿到的一份 repo 就是完整體
（overlay＋panel＋編輯器）。拆出去反而製造「編輯器版本 × 資料格式版本」的相容矩陣，
而使用者只有一人維護（bus factor = 1），多一個部署就多一份長期負擔。

### 保留未來拆分的退路（現在就要做的事）

編輯器的**核心邏輯不寫在 UI 裡**，寫成 isomorphic 純函數模組（與 chatProcessor.js 同款模式）：
- `yuupeek/src/packFormat.js` — 角色包驗證/正規化/匯入匯出（規格見 character-pack-format.md）
- UI（panel 分頁或 editor.html）只呼叫這些模組。
將來若真要拆獨立站，把模組拿走即可，UI 重寫成本低。這條同時是給弱模型的護欄：
**格式邏輯改動＝改模組＋跑測試，不准散落在 HTML 內嵌 script 裡**。

## 影響

- 新功能的部署影響評估基準：「舊 overlay＋新資料」與「新 overlay＋舊資料」都必須能跑
  （使用者 OBS 快取的頁面與 RTDB 資料不會同時更新）。
- 市集是唯一需要「中央」的東西：解法必須是零成本靜態方案（GitHub registry），
  詳 docs/designs/marketplace.md；若未來走付費角色才重新評估 Blaze／中央服務。

## 若要推翻本決策

推翻「不拆編輯器」的合理訊號：出現多維護者、或市集使用者量大到需要中央 web 編輯體驗。
屆時開新 ADR 重新評估（回顧本檔選項 B 的缺點清單是否仍成立），不要直接改本檔結論。
